# RTP decoded output and presentation evidence v1

An encoded access unit, decoder input, releaseBuffer intent, enqueue call or nonempty unassociated buffer never proves decoded or displayed progress. Decoder output has its own strictly advancing per-owner sequence and monotonic arrival clock. Source packet activity cannot extend that clock. Renderer submission and a platform-confirmed presentation callback/identified displayed output are separate levels. No level proves that the user saw physical pixels.

Each monitor sample is bound to one source owner, renderer generation, monotonically unique frame token and LUT revision. An output captured before a LUT change cannot describe the new revision, even if dimensions and pixel values happen to match. Analysis must use the exact decoded/processed image (or same GL draw readback), not asynchronous PixelCopy or an unidentifiable display snapshot attributed to an earlier frame. A flat static scene is legitimate; image hashes are not freshness.

`evaluateRtpMonitorEvidence` has three independent result fields. `canPublishDecodedAnalysis` permits exact decoded/processed-output analysis with its evidence label. `canPublishSubmittedAnalysis` additionally requires that exact output was accepted by the rendering surface. `canClaimPresentation` additionally requires an actual platform callback or positively identified displayed output. Browser Image.decode plus exact image insertion remains decoded-output; EGL successful swap is surface-submitted. Decoded-only or submitted-only scopes must not be described as confirmed display pixels. Unknown evidence rejects all three. This pure gate cannot authenticate a producer's claimed evidence.

In this pure sampling gate, `currentFrame` identifies the retained authoritative output-evidence record being sampled. It need not be the newest global live frame: asynchronous histograms/waveforms may finish for a bounded recent sample while reporting that sample identity, age and evidence level. `currentLut`, owner and renderer must still match current configuration. Spatial overlays drawn over the current video require the additional exact-current-display-frame check; a histogram sample's historical presentation confirmation is not evidence of current display progress.

All outputs require an active nonterminal source, exact owner and renderer, pending original Stop duty, matching positive frame tokens and nonnegative LUT revisions, explicit foreground policy, and sample/output ages within a positive bound of at most 5000 ms. Desktop may explicitly retain foregroundRequired=false. Missing, malformed, future/negative, unsafe-number or stale identity values fail closed. Equality at the bound is accepted; a runtime watchdog may retire earlier, which then makes active=false.

Only actual new decoded output advances decoder liveness. Only a new positively identified presented token advances presentation liveness. Re-reading the same displayed buffer or receiving callbacks with repeated/out-of-order tokens cannot keep a dead renderer alive. An unsupported or unidentifiable presentation API is explicit unverified capability, not evidence of camera failure. A renderer which previously supplied reliable progress and then freezes is bounded and retired through the existing exact-owner failure/Stop path. Local teardown does not acknowledge camera Stop. No unknown Start is replayed, and AUTO cannot replace an admitted source until original Stop is confirmed.

Foreground restoration, LUT replacement, terminal failure and owner replacement clear obsolete monitor/presentation evidence and retire old callbacks. Resource ownership must be retained until physical work really ends; logical cancellation must not free a busy decoder/GPU slot for unsafe reuse. Native decoding/rendering and physical-camera/weak-network performance remain separate authored/not-run acceptance obligations.
