# Ordinary shooting-setting journey alignment

Implementation scope: existing exposure, white balance, advertised choice/range/text and structured settings. Selection and Apply are separate on all three UIs, including actual camera photo/video mode. A mode selector without a camera-mode property changes only local UI. Recording, uncertain Stop and Bulb responsibilities remain prior gates.

Each attempt freezes session object, actual transport/engine, exact requested key/value, editor/revision and one route. The UI keeps bounded20 receipts, honest response/readback evidence, cancellation and explicit bounded read-only recovery. Current camera values come only from valid observations, never requested-value cache assignments. Full structured WB/image-quality siblings are read and validated before a write. Events update observations/abilities without silently replacing intent; stale reads cannot erase newer scoped results.

New bridge POST /settings/{key}/outcome and GET /settings/{key} are additive. The old POST remains compatible. The new UI does not fall back to it after an error. CCAPI and libgphoto2 implement scoped outcomes. External EDSDK providers lack this optional contract and fail before dispatch; their scoped outcome UI integration remains unavailable pending provider support, not claimed aligned.

Transport evidence: complete successful transport responses do not prove exact camera acknowledgment or causal application. Unknown responses never upgrade from a later matching read. CCAPI freezes one advertised route; one strict fresh canonical/aggregate read validates ordinary values. gphoto2 uses --get-config for the exact previously advertised path, plus storage-info only when recording-card safety requires it; requested values never become observed cache. Android standard PTP freshly reads its property descriptor. Canon USB updates event-derived advertised ability from a strict pending-event drain; this is not proof of a newly fetched complete descriptor when no ability event arrives. Exact Canon readback requires a newly requested matching property-value event; unsupported request capability yields read-unavailable. No remote/event-mode preparation mutation is hidden in recovery.

Read limits: PC scoped lock plus camera reads use a15-second cooperative budget,64KiB HTTP/config response bound, complete/unique JSON or scoped CLI fields, and no redirect or alias write replay. urllib DNS/header and blocking reads can overrun the cooperative budget; late values are rejected, not forcibly killed. UI write and recovery deadlines remain bounded. Native source/tests describe their actual deadlines; local source or pure-JVM tests do not prove native scheduling or camera responsiveness.

Validation boundary: contract policy vectors, Python/Node logic and pure JVM/source checks are local evidence. Swift/Xcode, Android SDK/Compose/MockWebServer, real browser pipeline and all physical-camera behavior remain separately pending unless an exact run receipt records execution. No camera or host media is mutated by synthetic tests. Current previously requested CI snapshot is unchanged by this local cohort.

Release assessment: patch-level reliability and behavior correction for existing controls; no version bump, release or merge requested here. Original development draft PRs remain drafts. Exact-head CI and physical-device claims are still separate gates.
