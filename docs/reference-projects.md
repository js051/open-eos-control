# Reference Projects And Validity Map

This project should stay grounded in public specifications, official platform APIs, and working open-source camera-control projects. Features must be marked as implemented only when the code path exists in this repo and has passed local tests.

## Primary References

- Canon CCAPI: Canon documents CCAPI as an HTTP-based API for controlling Canon cameras over a network, usable from a smartphone, tablet, or computer. Reference: [Canon CCAPI product manual](https://cam.start.canon/en/C017/manual/html/UG-06_Network_0130.html).
- Canon CAP release status: Canon's public release notes list CameraControlAPI Reference v1.4.0 Rev.1.4 as of March 31, 2026. Canon's public Camera API page lists deletion of images on storage media as a CCAPI/EDSDK capability; the API specification and official Android sample distributed through CAP remain the conformance source for endpoint payloads. References: [Canon Camera API Package](https://asia.canon/en/campaign/developerresources/cap), [Canon CAP overview](https://asia.canon/en/campaign/developerresources/camera/cap/cap), [CCAPI release notes](https://asia.canon/en/campaign/developerresources/camera/cap/camera-control-api-release-note).
- Canon CCAPI date and time: the public CCAPI reference defines readable and writable `/functions/datetime`, with an RFC 1123 `datetime` containing a numeric UTC offset and a separate boolean `dst`; its note requires the date/time value itself to account for daylight saving time. Open EOS Control advertises clock synchronization only when both GET and PUT are discovered, validates both write and read responses, and accepts success only when the readback is within ten seconds and has the requested DST state. Canomate provides tested open-source corroboration of the same endpoint and payload on Canon EOS bodies. References: [pinned CCAPI reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf), [pinned Canomate implementation](https://github.com/horshack-dpreview/Canomate/blob/7764bc532e06bc6d973dc6970d70b2059aefade8/canomate.py).
- Canon EOS clock synchronization through libgphoto2: the current generated R6 Mark III configuration snapshot explicitly exposes writable `syncdatetimeutc` and `syncdatetime` actions. Pinned libgphoto2 maps those actions to Canon EOS UTC/CameraTime properties and writes the host's current time. The Desktop Bridge prefers `syncdatetimeutc`, falls back to `syncdatetime`, and marks the command observed only after gphoto2 succeeds; the action widget does not provide an independent post-write clock readback, so diagnostics and documentation do not claim CCAPI-equivalent verification. References: [pinned R6 Mark III snapshot](https://github.com/gphoto/libgphoto2/blob/cc81290cf1d2a6101ff71487ac96dde772f9efb9/camlibs/ptp2/cameras/canon-eos-r6-markIII.txt), [pinned libgphoto2 Canon time mapping](https://github.com/gphoto/libgphoto2/blob/cc81290cf1d2a6101ff71487ac96dde772f9efb9/camlibs/ptp2/config.c).
- Canon CCAPI developer-list fallback: a pinned public mirror of Canon's Android CCAPI 1.3 sample recognizes the exact root response `{"value":"No list of APIs"}`, then requests `/ccapi/ver100/topurlfordev` and parses that response as the complete versioned operation list. Android, iOS, and the PC direct CCAPI engine follow only this exact marker and endpoint; a failed developer-list request remains a discovery error and never creates inferred capabilities. This mirror is corroborating implementation evidence, while the CAP-distributed specification and sample remain the conformance source. References: [pinned Canon sample discovery flow](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/MainActivity.java), [pinned Canon sample URL builder and response parser](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/WebAPI.java), [pinned marker and path constants](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/Constants.java).
- Canon CCAPI event polling: CCAPI 1.3 Reference section 4.4 defines `GET` and `DELETE /event/polling`, the v1.0 `continue=on` mode, and the v1.1+ `timeout=immediately|short|long` modes. Its response is a partial object containing only changed fields, not a complete camera snapshot. The pinned Canon Android sample runs the long poll on a dedicated thread, uses `continue=on` for v1.0 or `timeout=long` for newer versions, loops after each response, and sends `DELETE` when stopping. Android, iOS, the PC CCAPI engine, Desktop Bridge clients, and the browser UI therefore advertise `EVENT_POLLING` only when both methods are discovered, bound each response, retain only sanitized top-level change keys, and refresh authoritative status/capabilities after a non-empty event. References: [pinned CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf), [pinned Canon event thread](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/EventThread.java).
- Canon CCAPI manual focus: a pinned public mirror of Canon's Android CCAPI 1.3 sample sends `POST /shooting/control/drivefocus` with a `value` string selected from `near1` through `near3` or `far1` through `far3`. Open EOS Control follows that request contract only when the camera advertises the POST operation. References: [Canon sample request builder](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/WebAPI.java), [Canon sample control UI](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/RemoteCaptureFragment.java).
- Canon CCAPI media thumbnails: Canon's public CAP overview explicitly lists acquisition of image thumbnails. The pinned Canon CCAPI 1.3 Android sample appends `?kind=thumbnail` to each non-directory content URL and decodes the bounded response as an image. Android, iOS, and the PC CCAPI engine implement that exact same-origin query contract only when `/contents` browsing is advertised; malformed, textual, empty, and oversized responses remain real errors. Android USB and the libgphoto2 Bridge therefore expose `LIVE_VIEW_MAGNIFICATION` only when this operation/widget is advertised and Live View is active. Open EOS Control exposes `AUTOFOCUS` only when that POST or a verified balanced half-press path is available, and always attempts the matching stop/release. - Canon CCAPI RTP Live View: Canon's CCAPI 1.3 API Reference sections 4.11.7, 4.11.8 and 6.2.23 define `GET rtpsessiondesc`, `POST rtp` with `action`/`ipaddress`, H.264/90 kHz video on the SDP video port, and AAC LATM/48 kHz audio. The pinned Canon Android sample writes the returned SDP, starts distribution to the client's Wi-Fi address, and opens the SDP in a video player. - Android camera-control orientation: Android documents that `sensor`/`fullSensor` ignore the user's rotation lock, while `user`/`fullUser` honor it and `Settings.System.ACCELEROMETER_ROTATION` is the public switch for default accelerometer-based screen rotation. Android 13+ can additionally store posture-specific rotation locks, with the active posture synchronized back to `ACCELEROMETER_ROTATION`. CameraX documents using an orientation listener when a camera screen keeps a locked layout but still needs direction-aware content. Public camera implementations supply the UI pattern: GrapheneOS Camera keeps capture activities at `nosensor`, checks `ACCELEROMETER_ROTATION`, and rotates selected controls; AOSP Camera gives atomic controls a `Rotatable` contract, swaps measure axes for `RotateLayout` content, and applies hysteresis around quadrant changes; Jetpack Camera App uses the same 5-degree hysteresis in a conflated orientation flow. Open EOS Control keeps capture geometry and panel anchors fixed, reads the public system policy before enabling its foreground listener, and reconciles it whenever the activity starts, resumes, regains focus, or receives a posture sample. Locking rotation immediately clears the previous posture and resolves controls to zero, and there is no persisted app-level bypass. Compact status and exposure atoms remain in square slots with full values available through readable detail surfaces. At quarter turns, guidance derives its readable long axis from the available Live View height, settings swap measurement axes across the full fixed panel, and warnings, long errors, status details, messages, and the action menu use bounded readable panels without moving capture controls or dropping localized copy. Unit, Compose, and AVD tests cover launch-time rotation lock preservation, live setting changes, stale-angle clearing, 90/180-degree placement, English and Traditional Chinese full-copy geometry, enlarged text, extreme exposure values, and hit-target separation. References: [Android activity orientation values](https://developer.android.com/guide/topics/manifest/activity-element#screen), [Android system rotation setting](https://developer.android.com/reference/android/provider/Settings.System#ACCELEROMETER_ROTATION), [device-state auto-rotate](https://source.android.com/docs/core/display/device-state-based-auto-rotate-setting), [CameraX rotation guidance](https://developer.android.com/media/camera/camerax/configuration#rotation), [AOSP Camera RotateImageView](https://android.googlesource.com/platform/packages/apps/Camera2/+/394baebc5579fa9c3f7e09bfbcac7ef666f6c002/src/com/android/camera/ui/RotateImageView.java), [AOSP Camera RotateLayout](https://android.googlesource.com/platform/packages/apps/Camera2/+/394baebc5579fa9c3f7e09bfbcac7ef666f6c002/src/com/android/camera/ui/RotateLayout.java), [AOSP Camera orientation manager](https://android.googlesource.com/platform/packages/apps/Camera2.git/+/bf824fc61a8b39b7bc671a40921c315d518c098b/src/com/android/camera/app/OrientationManagerImpl.java), [GrapheneOS Camera manifest](https://github.com/GrapheneOS/Camera/blob/84aa73ab107ab2d38ce253d47a0bd71f25b88a3e/app/src/main/AndroidManifest.xml), [GrapheneOS control rotation](https://github.com/GrapheneOS/Camera/blob/84aa73ab107ab2d38ce253d47a0bd71f25b88a3e/app/src/main/java/app/grapheneos/camera/ui/activities/MainActivity.kt#L1188-L1229), [Jetpack Camera App debounced orientation flow](https://github.com/google/jetpack-camera-app/blob/57371e0df1dce7ce8d0944555ed0e8f826abd98f/ui/components/capture/src/main/java/com/google/jetpackcamera/ui/components/capture/DebouncedOrientationFlow.kt).

- libgphoto2 / gPhoto: libgphoto2 is the main open-source reference for camera access/control and PTP-backed Canon EOS tethering. The pinned gphoto2 CLI implementation defines argument-free `--capture-movie` as an endless loop over `gp_camera_capture_preview`, verifies JPEG MIME, and writes concatenated frames to stdout when requested; Open EOS Control uses this as its cancellable USB MJPEG path. Its pinned event action accepts bounded millisecond waits and emits stable `UNKNOWN`, `CAPTURECOMPLETE`, `FILEADDED`, `FOLDERADDED`, and `FILECHANGED` markers; the Bridge probes that real command before advertising event synchronization and parses only those markers. Its pinned capture implementation calls `gp_camera_capture`, downloads each returned or queued `FILE_ADDED` path, and deletes the camera object only after a successful download unless `--keep` is selected. The filename formatter supports an increasing `%n` and original extension `%C`; Open EOS Control therefore uses `--capture-image-and-download` with a unique `%04n.%C` staging template for host-RAM RAW+JPEG capture instead of inventing Canon PTP commands. The CLI manual defines both `--get-thumbnail RANGE or NAME` and `--get-file RANGE or NAME` with `--stdout`; the Bridge uses the latter as a bounded display-preview read only for listed JPEG/PNG items, while full downloads keep the existing streamed path. ## Open-Source Behavior To Mirror

- Capability-driven UI: libgphoto2 exposes configuration and capture support per camera model, so Open EOS Control must expose backend capabilities instead of assuming every camera/transport supports every command.
- EOS USB control path: gPhoto lists many Canon EOS R bodies, including EOS R6 and R6 Mark II, with image capture, trigger capture, liveview, and configuration support. R6 Mark III still needs direct validation, so it remains this project's golden test target rather than a claimed upstream-supported body.
- Desktop bridge path: the PC bridge should follow the libgphoto2 model first. Canon EDSDK can be an optional local adapter, but proprietary SDK binaries must not be committed or redistributed here.

## Current Validity Map

Implemented and test-covered:

- Camera clock synchronization across Android, iOS, and PC: direct CCAPI requires advertised GET+PUT and verifies the returned date/DST, while the USB Desktop Bridge invokes only camera-advertised writable libgphoto2 synchronization actions and reports that command-level limitation.
- CCAPI network backend shape, same-origin canonical `url` and relative `path` discovery parsing, bounded event polling with authoritative state refresh, simulator contract, scalar dynamic settings plus Canon's object-valued RAW/JPEG/HEIF image quality and B/A/M/G white-balance shift, recording, Canon `afframeposition` Tap AF and `clickwb` Click White Balance backed by detailed Live View geometry, advertised `drivefocus` Near/Far control, JPEG live view polling, Android/iOS/PC RTP H.264 video, still/manual shutter and held Bulb press/release control, paged media browsing, streaming media download, and deletion gated by an advertised `DELETE` operation.

## Development Rule

Do not mark a feature as supported unless both conditions are true:

1. The repo contains an executable code path for that feature.
2. The feature is covered by automated tests, simulator tests, or a recorded real-device validation note.

Otherwise expose it as `planned`, `research`, or `unsupported`.
