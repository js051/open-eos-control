# Reference Projects And Validity Map

This project should stay grounded in public specifications, official platform APIs, and working open-source camera-control projects. Features must be marked as implemented only when the code path exists in this repo and has passed local tests.

## Primary References

- Canon CCAPI: Canon documents CCAPI as an HTTP-based API for controlling Canon cameras over a network, usable from a smartphone, tablet, or computer. Reference: [Canon CCAPI product manual](https://cam.start.canon/en/C017/manual/html/UG-06_Network_0130.html).
- Canon CAP release status: Canon's public release notes list CameraControlAPI Reference v1.4.0 Rev.1.4 as of March 31, 2026. Canon's public Camera API page lists deletion of images on storage media as a CCAPI/EDSDK capability; the API specification and official Android sample distributed through CAP remain the conformance source for endpoint payloads. References: [Canon Camera API Package](https://asia.canon/en/campaign/developerresources/cap), [Canon CAP overview](https://asia.canon/en/campaign/developerresources/camera/cap/cap), [CCAPI release notes](https://asia.canon/en/campaign/developerresources/camera/cap/camera-control-api-release-note).
- Canon CCAPI event polling: CCAPI 1.3 Reference section 4.4 defines `GET` and `DELETE /event/polling`, the v1.0 `continue=on` mode, and the v1.1+ `timeout=immediately|short|long` modes. Its response is a partial object containing only changed fields, not a complete camera snapshot. The pinned Canon Android sample runs the long poll on a dedicated thread, uses `continue=on` for v1.0 or `timeout=long` for newer versions, loops after each response, and sends `DELETE` when stopping. Android, iOS, the PC CCAPI engine, Desktop Bridge clients, and the browser UI therefore advertise `EVENT_POLLING` only when both methods are discovered, bound each response, retain only sanitized top-level change keys, and refresh authoritative status/capabilities after a non-empty event. References: [pinned CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf), [pinned Canon event thread](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/EventThread.java).
- Canon CCAPI manual focus: a pinned public mirror of Canon's Android CCAPI 1.3 sample sends `POST /shooting/control/drivefocus` with a `value` string selected from `near1` through `near3` or `far1` through `far3`. Open EOS Control follows that request contract only when the camera advertises the POST operation. References: [Canon sample request builder](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/WebAPI.java), [Canon sample control UI](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/RemoteCaptureFragment.java).
- Canon CCAPI media thumbnails: Canon's public CAP overview explicitly lists acquisition of image thumbnails. The pinned Canon CCAPI 1.3 Android sample appends `?kind=thumbnail` to each non-directory content URL and decodes the bounded response as an image. Android, iOS, and the PC CCAPI engine implement that exact same-origin query contract only when `/contents` browsing is advertised; malformed, textual, empty, and oversized responses remain real errors. References: [Canon CAP overview](https://asia.canon/en/campaign/developerresources/camera/cap/cap), [pinned Canon `ContentsAdapter`](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Sample/Android/Sample/Sample/app/src/main/java/com/canon/ccapisample/ContentsAdapter.java).
- Canon CCAPI media display preview: the pinned Canon Android sample maps its display action to `kind=display`, passes that query into the content-show screen, and opens the returned representation inside the app. Open EOS Control follows that exact structured query only for same-origin image/RAW items, advertises it separately from thumbnails, limits responses to 32 MiB, and rejects text or unrecognized images. References: [pinned `ContentsViewerFragment`](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Sample/Android/Sample/Sample/app/src/main/java/com/canon/ccapisample/ContentsViewerFragment.java), [pinned `ContentsShowFragment`](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Sample/Android/Sample/Sample/app/src/main/java/com/canon/ccapisample/ContentsShowFragment.java).
- Canon EOS Live View focus magnification: Canon CCAPI Reference 1.3 defines `/shooting/control/zoom` as PowerShot built-in optical zoom and marks it unsupported for non-PowerShot cameras, so Open EOS Control does not expose that endpoint as EOS focus magnification. The pinned R6 Mark III libgphoto2 snapshot separately advertises writable `/main/actions/eoszoom`; pinned libgphoto2 maps it to Canon EOS PTP `Zoom (0x9158)`, sends one integer parameter, and documents 1 and 5 as the known working values. Android USB and the libgphoto2 Bridge therefore expose `LIVE_VIEW_MAGNIFICATION` only when this operation/widget is advertised and Live View is active. References: [pinned CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf), [pinned R6 Mark III snapshot](https://github.com/gphoto/libgphoto2/blob/ce6c5f7c7fdde404e9897f618df6168c01df70f5/camlibs/ptp2/cameras/canon-eos-r6-markIII.txt), [pinned Canon config mapping](https://github.com/gphoto/libgphoto2/blob/ce6c5f7c7fdde404e9897f618df6168c01df70f5/camlibs/ptp2/config.c), [pinned operation definition](https://github.com/gphoto/libgphoto2/blob/ce6c5f7c7fdde404e9897f618df6168c01df70f5/camlibs/ptp2/ptp.h).
- Canon CCAPI autofocus: the same pinned Canon Android sample sends `POST /shooting/control/af` with `{"action":"start"}` and `{"action":"stop"}`. Open EOS Control exposes `AUTOFOCUS` only when that POST or a verified balanced half-press path is available, and always attempts the matching stop/release. References: [Canon sample request builder](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/WebAPI.java), [Canon sample remote capture flow](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/RemoteCaptureFragment.java).
- Canon CCAPI Bulb shutter: the pinned Canon Android sample's manual shutter flow sends `full_press` and a separate `release` to the advertised manual shutter endpoint. Open EOS Control uses that split lifecycle only when the operation is advertised, sets `af=false` for the held exposure, does not query status between press and release, and keeps stop retryable after failure. References: [Canon sample request builder](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/WebAPI.java), [Canon sample manual-shutter flow](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/RemoteCaptureFragment.java).
- Canon CCAPI coordinate Tap AF: the pinned Canon Android sample reads `image.positionx`, `positiony`, `positionwidth`, and `positionheight` from `flipdetail?kind=both`, maps the displayed-image touch into that camera coordinate space, and sends `PUT /shooting/liveview/afframeposition` with integer `positionx` and `positiony`. Open EOS Control implements this exact bounded packet/metadata flow on Android, iOS, and the PC CCAPI engine; it never sends guessed normalized coordinates. References: [Canon sample request builder](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/WebAPI.java), [touch-coordinate mapping](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/RemoteCaptureFragment.java), [detailed Live View parser](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/OrgFormatDataSet.java).
- Canon CCAPI Click White Balance: the same pinned Canon sample maps the displayed-image touch through detailed Live View geometry and sends `POST /shooting/liveview/clickwb` with integer `positionx` and `positiony`. Open EOS Control uses that exact capability-gated contract on Android, iOS, and the PC CCAPI engine; USB/PTP and libgphoto2 do not expose it without separate verified command evidence. References: [Canon sample request builder](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/WebAPI.java), [Canon sample remote-capture UI](https://github.com/Chieri-JN/Intervelo/blob/bb826a1211c49a6d3a569ec8c4b9934b585db270/CCAPI_Sample_Android_1.3.0e/Sample/app/src/main/java/com/canon/ccapisample/RemoteCaptureFragment.java).
- Canon CCAPI still image quality: CCAPI 1.3 Reference sections 4.9.15 and 6.2.16 define object-valued `stillimagequality` with camera-advertised RAW and JPEG/HEIF leaves and a `PUT` body shaped as `{"value":{"raw":"...","jpeg":"..."}}` (or HEIF on supported versions). Android, iOS, and the PC CCAPI engine expose those advertised leaves separately, preserve companion values on each write, and reject disabling every available still format. Reference: [pinned CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf).
- Canon CCAPI white-balance shift: CCAPI 1.3 Reference section 4.9.25 defines object-valued `wbshift`, integer `ba`/`mg` leaves, per-axis `min`/`max`/`step` ability ranges, and a complete nested `PUT` value. Android, iOS, and PC generate at most 256 exact in-range options per axis, preserve the companion axis, and send integers rather than UI strings. Reference: [pinned CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf).
- Canon CCAPI RTP Live View: Canon's CCAPI 1.3 API Reference sections 4.11.7, 4.11.8 and 6.2.23 define `GET rtpsessiondesc`, `POST rtp` with `action`/`ipaddress`, H.264/90 kHz video on the SDP video port, and AAC LATM/48 kHz audio. The pinned Canon Android sample writes the returned SDP, starts distribution to the client's Wi-Fi address, and opens the SDP in a video player. Open EOS Control implements RFC 3550 packet parsing and RFC 6184 H.264 depacketization on Android, iOS, and PC. Android renders through `MediaCodec`; iOS uses Wi-Fi-only Network.framework listeners and `AVSampleBufferVideoRenderer`; PC binds the routed local IPv4/UDP port, decodes with PyAV/FFmpeg, and converts selected decoded frames to JPEG for the stable Bridge API. Audio remains unsupported. Open EOS Control uses this only as reproducible evidence for the discovery response shape; it does not substitute for R6 Mark III validation. - Android network routing and validation: Android documents binding sockets to a selected `Network`, inspecting synchronous network snapshots for occasional diagnostics, and using `NET_CAPABILITY_VALIDATED` as the system signal that a network has actual public-internet access rather than merely being configured for internet. Open EOS Control binds only camera sockets to the camera Wi-Fi and uses the validated system-default network snapshot for its coexistence diagnostic; it does not bind the whole process. - Android camera-control orientation: Android documents that `sensor`/`fullSensor` ignore the user's rotation lock while `Settings.System.ACCELEROMETER_ROTATION` is the public switch controlling default accelerometer-based screen rotation. Pixel Camera Help confirms that on-screen camera instructions stay fixed when auto-rotation is disabled. A fixed-layout camera UI needs a different pattern: the pinned GrapheneOS Camera keeps its capture activities at `nosensor`, checks that system setting on every orientation callback, and rotates only selected controls and its settings frame. AOSP Camera's single-child `RotateLayout` swaps width/height measurement before quarter-turn rotation, while its full `RotatableLayout` changes child gravity, margins and dimensions to keep controls on the correct physical edge. Google's pinned Jetpack Camera App adds a 5-degree hysteresis before snapping sensor angles to a new quadrant. Open EOS Control combines those public patterns: the sensor listener stays active while the Activity is started so a missed quick-settings observer cannot leave stale rotation, but every sample re-reads the public auto-rotate setting and locked mode always resolves to zero control rotation. Observer, focus-return reconciliation and a bounded poll remain additional safeguards. Capture geometry stays fixed; compact HUD atoms rotate inside stable slots, while longer guidance exchanges measurement axes against the full Live View viewport. Settings change container geometry as well as content measurement: bottom in portrait, full-height side placement for quarter turns, and top placement for a natural-coordinate 180-degree turn, which keeps the sheet on the user's physical bottom edge without recreating camera state. Camera identity, battery and storage use compact visible values with full accessibility descriptions. Unit, Compose and AVD tests cover the real system setting, live lock changes with an open panel, 90/180-degree panel placement, long English labels, and localized copy at 1.5x font scale. ## Open-Source Behavior To Mirror

- Capability-driven UI: libgphoto2 exposes configuration and capture support per camera model, so Open EOS Control must expose backend capabilities instead of assuming every camera/transport supports every command.
- EOS USB control path: gPhoto lists many Canon EOS R bodies, including EOS R6 and R6 Mark II, with image capture, trigger capture, liveview, and configuration support. R6 Mark III still needs direct validation, so it remains this project's golden test target rather than a claimed upstream-supported body.
- Desktop bridge path: the PC bridge should follow the libgphoto2 model first. Canon EDSDK can be an optional local adapter, but proprietary SDK binaries must not be committed or redistributed here.

Implemented and test-covered:

- CCAPI network backend shape, same-origin canonical `url` and relative `path` discovery parsing, bounded event polling with authoritative state refresh, simulator contract, scalar dynamic settings plus Canon's object-valued RAW/JPEG/HEIF image quality and B/A/M/G white-balance shift, recording, Canon `afframeposition` Tap AF and `clickwb` Click White Balance backed by detailed Live View geometry, advertised `drivefocus` Near/Far control, JPEG live view polling, Android/iOS/PC RTP H.264 video, still/manual shutter and held Bulb press/release control, paged media browsing, streaming media download, and deletion gated by an advertised `DELETE` operation.
- Android USB host diagnostics: enumerate devices, identify Canon vendor ID `0x04A9`, identify PTP still-image interfaces, show endpoints, and request Android USB permission.
- Android standards-based USB/PTP path: claim the interface, open/close a session, parse DeviceInfo, property, storage and object datasets, safely write bounded camera-advertised standard properties, conditionally issue advertised standard still capture, browse media, retrieve bounded embedded thumbnails with standard `GetThumb (0x100A)`, read bounded JPEG/PNG display previews and stream downloads with `GetObject (0x1009)`, and issue exact-handle `DeleteObject` only when advertised.
- Android Canon EOS USB path: capability-gated remote/event setup, native DoAf/AfCancel with half-press fallback, shooting mode, ISO/Tv/Av/WB, exposure compensation, color temperature, signed WB shifts, color space, aspect ratio, power-zoom speed, Auto Power Off, High ISO noise reduction and AEB event state/writes, selectable Phone/Memory card capture destination only when both paths are executable, balanced release and event confirmation, timed half-press, Card/None movie control, Near/Far focus drive, advertised 1x/5x Live View focus magnification, EVF start/stop, and in-memory JPEG Live View parsing.
- Desktop Bridge service, libgphoto2 CLI adapter, direct PC CCAPI engine, and Android/iOS bridge clients: authenticated sessions, dynamic settings/capabilities, capture, focus, JPEG preview, advertised RTP receive/decode on PC, capability-gated media thumbnails, media streaming/deletion and deterministic contract tests. The libgphoto2 path uses the R6 Mark III snapshot's paired autofocus drive/cancel actions when both runtime widgets are writable, maps WB shifts, per-card image quality, aspect ratio, power-zoom speed, documented Auto Power Off values and recognized Capture Target choices only when writable runtime choices exist, and blocks the unknown power sentinel. Card capture remains on camera; host RAM uses the pinned gPhoto2 capture/download/delete lifecycle and exposes only successfully promoted local media through opaque IDs. Camera-resident thumbnail and deletion remain gated by runtime abilities.
- Multi-backend contract: unsupported operations throw explicit transport/feature errors.

## Development Rule

Do not mark a feature as supported unless both conditions are true:

1. The repo contains an executable code path for that feature.
2. The feature is covered by automated tests, simulator tests, or a recorded real-device validation note.

Otherwise expose it as `planned`, `research`, or `unsupported`.
