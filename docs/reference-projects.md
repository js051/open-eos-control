# Reference Projects And Validity Map

This project should stay grounded in public specifications, official platform APIs, and working open-source camera-control projects. Features must be marked as implemented only when the code path exists in this repo and has passed local tests.

## Primary References

- Canon EOS Auto Lighting Optimizer: pinned libgphoto2 defines `AloMode (0xD1C1)`, maps its user values through a `Generic32` table, and parses the EOS property as UINT32. The generated R6 Mark III snapshot currently exposes only `x3`; Open EOS Control preserves that as capability evidence but requires at least two camera-advertised values from the pinned safe table before exposing a writable control. References: [R6 Mark III snapshot](https://github.com/gphoto/libgphoto2/blob/ce6c5f7c7fdde404e9897f618df6168c01df70f5/camlibs/ptp2/cameras/canon-eos-r6-markIII.txt), [Canon ALO mapping](https://github.com/gphoto/libgphoto2/blob/ce6c5f7c7fdde404e9897f618df6168c01df70f5/camlibs/ptp2/config.c), [property code](https://github.com/gphoto/libgphoto2/blob/ce6c5f7c7fdde404e9897f618df6168c01df70f5/camlibs/ptp2/ptp.h), [event parser](https://github.com/gphoto/libgphoto2/blob/ce6c5f7c7fdde404e9897f618df6168c01df70f5/camlibs/ptp2/ptp-pack.c).
- Canon CCAPI: Canon documents CCAPI as an HTTP-based API for controlling Canon cameras over a network, usable from a smartphone, tablet, or computer. Reference: [Canon CCAPI product manual](https://cam.start.canon/en/C017/manual/html/UG-06_Network_0130.html).
- Standard PTP/MTP media upload: Android's public `MtpDevice` API exposes the standard `SendObjectInfo` then `SendObject` lifecycle, while pinned libgphoto2 sends the same two transactions and streams the exact declared object size from a data handler. The responder may return the selected storage, parent and newly allocated object handle from `SendObjectInfo`; a root upload uses the standard all-ones parent handle. Open EOS Control therefore enables direct Android USB upload only when both operations, a writable storage and a matching camera-advertised object format are present, then requires exact `GetObjectInfo` readback before reporting success. References: [Android `MtpDevice`](https://developer.android.com/reference/android/mtp/MtpDevice), [pinned libgphoto2 PTP transactions](https://github.com/gphoto/libgphoto2/blob/77a6c7008539ba2e0cda83c1a71014686fe4374b/camlibs/ptp2/ptp.c#L2647-L2725), [pinned libgphoto2 upload path](https://github.com/gphoto/libgphoto2/blob/77a6c7008539ba2e0cda83c1a71014686fe4374b/camlibs/ptp2/library.c#L9130-L9180).
- gPhoto2 media upload: the CLI's documented `--folder`, `--filename`, and `--upload-file` path delegates to `gp_camera_folder_put_file`. The Desktop Bridge advertises `MEDIA_UPLOAD` only after runtime evidence reports file upload and a writable storage; it stages an exact bounded request body, invokes that argument-array command without a shell, and requires one matching name/size in a fresh media listing. References: [pinned gPhoto2 upload action](https://github.com/gphoto/gphoto2/blob/70e83ed3fd630c656e7859f2a510b70bc20b50b8/gphoto2/actions.c#L75-L125), [pinned gPhoto2 CLI option](https://github.com/gphoto/gphoto2/blob/70e83ed3fd630c656e7859f2a510b70bc20b50b8/gphoto2/main.c#L2140-L2160).
- Canon EOS R6 Mark III firmware 1.1.0: Canon's July 22, 2026 notice states that this release adds EDSDK/CCAPI support. A post-update zero-command report therefore cannot by itself prove that firmware removed camera controls; it more plausibly exposes a discovery compatibility issue, especially when identity and battery remain reachable. Open EOS Control still treats the exact developer operation list as authoritative and never enables an endpoint from the firmware version or model name alone. Reference: [Canon EOS R6 Mark III firmware 1.1.0 notice](https://www.usa.canon.com/support/canon-product-advisories/Firmware-Notice-EOS-R6-Mark-III-Firmware-Version-1-1-0).
- EOS R6 Mark III firmware: Canon's official firmware 1.1.0 notice explicitly adds EDSDK/CCAPI support. A firmware update can therefore change the discovery surface, but Open EOS Control must parse each valid advertised operation independently and never assume every model or firmware exposes the same command set. Reference: [Canon EOS R6 Mark III firmware 1.1.0 notice](https://www.usa.canon.com/support/canon-product-advisories/Firmware-Notice-EOS-R6-Mark-III-Firmware-Version-1-1-0).
- Canon CCAPI recordable information: CCAPI Reference 1.3 section 4.5.1 defines `GET /shooting/information/recordable`. Its response contains both nullable integer fields: `recordableshots` is the remaining still-image count and is null in movie mode; `remainingtime` is remaining movie time in seconds and is null in still mode. Open EOS Control therefore accepts only the advertised endpoint and exact nonnegative integral/null contract, exposes successful values in Android, iOS and PC HUDs and diagnostics, and leaves the feature planned after malformed data. Physical R6 Mark III discovery and mode-transition evidence is still required. Reference: [pinned Canon CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf).
- Canon CCAPI dual-card selection: CCAPI Reference 1.3 sections 4.5.30 and 4.5.31 define separate readable/writable `/functions/cardselection/stillimage` and `/functions/cardselection/movie` resources. Each GET returns a string `value` plus string-array `ability`; the documented values are `none`, `card1`, and `card2`. PUT sends the selected value and returns HTTP 200 with the current value. Open EOS Control requires an advertised same-version GET/PUT pair, validates the complete finite value set without coercion or duplicates, and exposes still/movie controls only in their matching Photo/Video context. Physical R6 Mark III slot mapping and transition evidence remains required. Reference: [pinned Canon CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf).
- Canon CCAPI sound recording level: CCAPI Reference 1.3 section 4.9.55 defines readable/writable `/shooting/settings/soundrecording/level`. GET returns an integer `value` plus integer `ability.min`, `ability.max` and `ability.step`; PUT sends `{"value":<integer>}` and returns HTTP 200 with the current integer. Canon documents HTTP 503 while the camera is busy, recording, in Still mode, or not using Manual sound recording. Open EOS Control therefore requires a same-version GET/PUT pair, bounds the generated range to 2-256 exact values, re-reads it before every write, and exposes a Video-only discrete slider. Physical R6 Mark III endpoint and Manual-mode transition evidence remains required. Reference: [pinned Canon CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf).
- Canon CCAPI sound recording controls: CCAPI Reference 1.3 sections 4.9.54, 4.9.56 and 4.9.57 define readable/writable `/shooting/settings/soundrecording`, `/shooting/settings/soundrecording/windfilter` and `/shooting/settings/soundrecording/attenuator`. GET returns a string `value` and string-array `ability`; PUT sends the selected string. Documented values are `auto|manual|disable`, `auto|enable|disable`, and `enable|disable|auto|manual` respectively. Canon documents HTTP 503 while busy, recording, in Still mode, or when sound recording is disabled for the child settings. Open EOS Control therefore requires exact same-version GET/PUT pairs, known unique values containing the current state and a fresh read before every write. Physical R6 Mark III endpoint and transition evidence remains required. Reference: [pinned Canon CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf).
- Canon CCAPI focus bracketing: CCAPI Reference 1.3 sections 4.9.58 through 4.9.61 define readable/writable `/shooting/settings/focusbracketing` plus `numberofshots`, `focusincrement` and `exposuresmoothing` child resources. The root and exposure-smoothing resources use documented `enable|disable` string values; shot count and focus increment use integer current/min/max/step contracts, with examples of 2-999 shots and 1-10 increment. PUT sends the selected exact string or integer. Canon documents HTTP 503 while busy, shooting or recording, and in Movie mode. Open EOS Control therefore validates the root before reading children, requires exact same-version GET/PUT pairs, bounds generated ranges to 1,024 values and re-reads the complete advertised group before each Photo-only write. Physical R6 Mark III endpoint and transition evidence remains required. Reference: [pinned Canon CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf).
- Canon CCAPI movie recording settings: CCAPI Reference 1.3 sections 4.9.50 through 4.9.53 define readable/writable `moviequality`, `highframerate`, `moviecropping`, and `movieformat`. GET returns a string current value plus string-array ability and PUT sends the selected exact string. High-frame-rate and cropping use `enable|disable`; format uses `raw|mp4`; movie quality encodes image size, frame rate, compression method/rate and optional crop in one underscore-delimited camera token. Canon documents HTTP 503 while busy, recording, or in Still mode. Open EOS Control requires exact same-version GET/PUT pairs, validates bounded unique abilities, re-reads the complete advertised movie group before each write, and formats quality only at the display layer. Physical R6 Mark III endpoint and transition evidence remains required. Reference: [pinned Canon CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf).
- Canon CCAPI camera beep and display-off timeout: CCAPI Reference 1.3 defines readable/writable `/functions/beep` and `/functions/displayoff`. Both GET responses contain a string current value and string-array ability, and PUT sends the selected exact string. Documented beep values are `enable|disable|disabletouch`; display-off values are the second strings `10|20|30|60|120|180`. Canon documents HTTP 400 for invalid parameters and HTTP 503 while busy, shooting or recording. Open EOS Control requires an exact same-version GET/PUT pair, at least two valid unique values containing the current state and a fresh group read before every write. Physical R6 Mark III endpoint and transition evidence remains required. Reference: [pinned Canon CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf).
- Canon CCAPI Auto Power Off and immediate camera sleep: CCAPI Reference 1.3 defines readable/writable `/functions/autopoweroff`. Its documented string values are `30|60|120|180|300|600|disable|immediately`; ordinary PUT returns HTTP 200 with the current value, while `immediately` returns HTTP 202, exits CCAPI and puts the camera to sleep. Canon documents HTTP 400 for invalid values and HTTP 503 while busy, shooting, recording or preparing. Open EOS Control therefore validates an exact same-version GET/PUT pair and fresh complete ability, excludes `immediately` from the timed selector, and exposes it only as a separately confirmed disconnecting action when explicitly advertised. The Bridge, Android and iOS clients do not infer equivalent immediate behavior from libgphoto2 or Canon USB Auto Power Off properties. Physical R6 Mark III timed and immediate transitions remain required. Reference: [pinned Canon CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf).
- Canon CCAPI sensor cleaning: CCAPI Reference 1.3 sections 4-98 through 4-100 define `POST /functions/sensorcleaning` with one required strict boolean field, `autopoweroff`. Success is exactly HTTP 200 with an empty object; invalid or missing parameters return 400, while busy, shooting/recording and unsupported-mode states return 503. Open EOS Control therefore enables the action only from the advertised POST, requires the exact success status, suspends event polling and Live View around the maintenance operation, and treats optional power-off as a disconnecting choice rather than guessing that the session remains alive. No equivalent USB or libgphoto2 command is claimed without separate public evidence. Physical R6 Mark III firmware 1.1.0 validation remains required. Reference: [pinned Canon CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf).

- Canon CCAPI capture-directory control: the official CameraControlAPI v1.4 reference defines `POST /functions/directory/createdirectory` with an empty or exact five-character ASCII `directoryname`, plus readable/writable `/functions/directory/directoryselection` whose current and ability values use Canon's three-digit directory number followed by the five-character name. Open EOS Control requires all three methods in one advertised API version, validates the complete finite selection response without coercion or duplicates, refreshes it after creation, and does not claim a libgphoto2 equivalent. Canon's February 2025 Android sample release notes separately identify Create Directory and Specify File Name as added sample functions. - Canon CCAPI file naming: the official CameraControlAPI v1.4 reference defines seven independent readable/writable resources under `/functions/filename`: still filename mode, two still user settings, movie index, reel number, clip number, and movie user-defined name. Canon uses exact response keys for each resource, integer `value` plus min/max/step ability for reel and clip, and fixed-length uppercase ASCII rules for the text fields. Open EOS Control requires all seven GET/PUT pairs in one advertised API version, validates every read before exposing `FILE_NAMING_CONTROL`, sends strings or integers with the endpoint-specific key, and verifies both the write response and a complete readback. No USB/PTP or libgphoto2 equivalent is inferred. Canon's February 2025 Android sample release notes identify Specify File Name as an official sample feature. Physical R6 Mark III field availability and body transitions on the installed firmware remain required. - Canon CCAPI lens and temperature status: CCAPI Reference sections 4.4.6 and 4.4.7 define `GET /devicestatus/lens` with exact boolean `mount` and string `name` fields, plus `GET /devicestatus/temperature` with 12 enumerated restriction states. The reference directs applications to change control behavior for release, movie recording and Live View restrictions. Open EOS Control therefore accepts only an advertised endpoint and strict documented payload, refreshes temperature immediately before affected start commands, and leaves stop/release cleanup callable. Contract tests prove this behavior; a fresh physical R6 Mark III discovery and transition record is still required. Reference: [pinned Canon CCAPI 1.3 API Reference mirror](https://github.com/laxei-app/HolyGrailController/blob/85ffbb93415d82513cb6a3c20ddd7073b9fd169e/30_refer/20_manual/API%20canon/ccapi-1.3.0d/Document/CameraControlAPI_Reference_v130_EN.pdf).
- Canon CCAPI date and time: the public CCAPI reference defines readable and writable `/functions/datetime`, with an RFC 1123 `datetime` containing a numeric UTC offset and a separate boolean `dst`; its note requires the date/time value itself to account for daylight saving time. Open EOS Control advertises clock synchronization only when both GET and PUT are discovered, validates both write and read responses, and accepts success only when the readback is within ten seconds and has the requested DST state. The generated R6 Mark III snapshot advertises `eosremoterelease` choices including `Press Full` and `Release Full`, which back the USB/Bridge Bulb lifecycle, and exposes Drive/Cancel Autofocus controls but advertises neither Touch AF nor Click White Balance. - Canon EOS USB Touch AF evidence: libgphoto2 names `TouchAfPosition (0x915B)` as a three-parameter Canon operation. Julian Schroden's pinned open-source PTP/IP implementation independently parses Live View sensor resolution segment `0x0E`, maps normalized coordinates to that width/height, sends `0x915B` parameters `[0x03, x, y]`, and follows it with a bounded focus press/release. Because USB PTP and PTP/IP share the Canon operation/data model above the transport, Android mirrors only this evidenced command shape while still requiring the connected USB DeviceInfo to advertise `0x915B`. Missing geometry or any rejected command remains an error. This is implementation evidence, not proof that R6 Mark III supports the command; its pinned snapshot currently does not advertise it. - Canon EOS USB Click White Balance evidence: pinned libgphoto2 defines `ClickWB (0x9157)` with exactly two `x,y` arguments. Its generated R6, R6 Mark II and R7 snapshots advertise the operation, while the current R6 Mark III snapshot does not. - MTP object rating: AOSP defines `Rating (0xDC8A)`, the four standard object-property operations `0x9801..0x9804`, and the corresponding MTP response codes. Pinned libmtp identifies Rating as `UINT16` user rating `0-100`, implements descriptor-driven typed reads/writes, and leaves Canon's separate `SetRating (0x9140)` parameters explicitly uncertain. Android direct USB therefore uses only the standard path, accepts writable Range/Enumeration descriptors that prove all six application values, maps 0-5 stars to `0/20/40/60/80/100` as a clearly labeled application convention, preserves non-integral reads as unknown, and requires exact same-handle readback. ## Open-Source Behavior To Mirror

- Capability-driven UI: libgphoto2 exposes configuration and capture support per camera model, so Open EOS Control must expose backend capabilities instead of assuming every camera/transport supports every command.
- EOS USB control path: gPhoto lists many Canon EOS R bodies, including EOS R6 and R6 Mark II, with image capture, trigger capture, liveview, and configuration support. R6 Mark III still needs direct validation, so it remains this project's golden test target rather than a claimed upstream-supported body.
- Desktop bridge path: the PC bridge should follow the libgphoto2 model first. Canon EDSDK can be an optional local adapter, but proprietary SDK binaries must not be committed or redistributed here.

## Current Validity Map

Implemented and test-covered:

- Camera clock synchronization across Android, iOS, and PC: direct CCAPI requires advertised GET+PUT and verifies the returned date/DST; direct Android USB requires an advertised Canon clock event, exact UINT32 property write, and matching event readback; the USB Desktop Bridge requires a complete libgphoto2 action/DATE pair and verifies a fresh camera-config readback.
- CCAPI network backend shape, same-origin canonical `url` and relative `path` discovery parsing, bounded event polling with authoritative state refresh, simulator contract, scalar dynamic settings plus Canon's object-valued RAW/JPEG/HEIF image quality and B/A/M/G white-balance shift, recording, Canon `afframeposition` Tap AF and `clickwb` Click White Balance backed by detailed Live View geometry, advertised `drivefocus` Near/Far control, same-version `lvzoom` 1x/5x/10x string ability with PUT/GET readback, JPEG polling and persistent multipart Live View, Android/iOS/PC RTP H.264 video and default-muted in-band AAC-LATM audio, still/manual shutter and held Bulb press/release control, paged media browsing, streaming media download, and deletion gated by an advertised `DELETE` operation. The `lvzoom` contract is taken from Canon CCAPI 1.4; the public [CCAPI release notes](https://asia.canon/en/campaign/developerresources/camera/cap/camera-control-api-release-note) and [supported camera/API list](https://asia.canon/en/campaign/developerresources/camera/cap/cap) identify the current specification and EOS R6 Mark III support.
- Android USB host diagnostics: enumerate devices, identify Canon vendor ID `0x04A9`, identify PTP still-image interfaces, show endpoints, and request Android USB permission.
- Android standards-based USB/PTP path: claim the interface, open/close a session, parse DeviceInfo, device/object property, storage and object datasets, safely write bounded camera-advertised standard properties, conditionally issue advertised standard still capture, browse media, retrieve bounded embedded thumbnails with standard `GetThumb (0x100A)`, read bounded JPEG/PNG display previews and stream downloads with `GetObject (0x1009)`, issue exact-handle `DeleteObject` only when advertised, and read/write standard MTP card-media ratings only after per-format descriptor and concrete-object validation with exact readback.

The libgphoto2 path uses the R6 Mark III snapshot's paired autofocus drive/cancel actions when both runtime widgets are writable, maps WB shifts, per-card image quality, aspect ratio, power-zoom speed, documented Auto Power Off values and recognized Capture Target choices only when writable runtime choices exist, exposes only writable printable-ASCII Owner/Artist/Copyright/Nickname TEXT paths and forces an exact same-path refresh after writing, and blocks the unknown power sentinel. It also exposes active recording card only when the writable `storageid` current value belongs to at least two live writable IDs from official `--storage-info`; strict revalidation precedes each exact runtime-ID write, and PC/Android/iOS render the shared Photo-only setting. Card capture remains on camera; host RAM uses the pinned gPhoto2 capture/download/delete lifecycle and exposes only successfully promoted local media through opaque IDs. Camera-resident thumbnail and deletion remain gated by runtime abilities.

## Development Rule

Do not mark a feature as supported unless both conditions are true:

1. The repo contains an executable code path for that feature.
2. The feature is covered by automated tests, simulator tests, or a recorded real-device validation note.

Otherwise expose it as `planned`, `research`, or `unsupported`.
