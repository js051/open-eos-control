## Implemented scope

- Existing multi-select rating, protect/unprotect, rotate and archive/unarchive controls now freeze the selected exact-ID roster and operation target. First occurrence and selection order are retained; filter-hidden rows and rows unloaded before or after opening the sheet remain visible through display-only selected snapshots. The sheet freezes the connection reference plus generation, and both UI callbacks and ViewModel admission reject a retired owner, including a delayed callback with reused exact IDs. An empty or over-1,000-unique-ID policy request is rejected without a write. No whole-card search or extra metadata admission GET is added.
- Eligibility is re-evaluated from the current loaded exact-ID row and current session capability before each dispatch. Explicit per-action `ratingWritable`, `protectionWritable`, `archiveWritable` and `rotationWritable` false values veto that operation. They never create capabilities. Archive additionally requires a known Boolean archive state; unknown or unloaded rows stay unstarted.
- A separate in-memory metadata receipt reports exact IDs, immutable target, awaiting-readback, confirmed, uncertain, failed-before-send and not-started rows. Same filenames on different IDs remain distinguishable. English and Traditional Chinese summaries, bounded scrollable rows, hidden/unloaded counts and Cancel remaining changes are available in the sheet and gallery.
- There is one mutation in flight and at most one write per item. The first uncertain response stops the remainder. Cancellation retains earlier confirmations and leaves untouched rows unstarted. A same-owner late exact return may remain confirmed. Owner/session replacement blocks later writes and publication into the replacement session. The previous connection’s receipt remains separately labeled; in-flight rows become uncertain while earlier confirmations and unstarted rows survive.
- Bridge write responses must report both the exact requested ID and exact target value for all four fields. Direct CCAPI retains its existing three bounded readbacks, now requiring explicit returned identity to match too. Canon's absent ID remains bound to the requested exact endpoint. No automatic mutation replay is added.
- Single-item mutation admission and dispatch now consult current exact-ID gallery, preview or capture-review metadata before the caller snapshot; a stale writable=true cannot override a current false veto or unknown archive state. Existing fresh-detail calls with no current matching record remain accepted under the prior capability rules. Four single-detail UI callbacks bind and verify the opening owner using the same live root owner reference. Public item-only ViewModel methods do not encode historical owner identity; an arbitrary external stale-owner call cannot be distinguished from a fresh detail call with reused IDs, so production UI owner fencing is required.
- Successful mutation cache updates merge only the verified target field into each current exact-ID item. Partial or unrelated response fields cannot erase existing writable vetoes, archive evidence or other metadata. Transport decoders retain their existing raw-response/folder-validation semantics.
- Before Android JSONTokener, media info/write responses, simulator listings and legacy Bridge listings use the existing listing grammar guard, now shared as `StrictMediaJson`. It rejects non-JSON syntax, comments, duplicate decoded keys and invalid Unicode; bounded strict UTF-8 reading precedes decoding. The raw guard is opt-in for media routes, leaving generic settings parsers untouched.
- Media-only decoding rejects coerced false/zero values, floats/exponents, malformed or missing fields, signed/padded/whitespace/Unicode digit strings and overflow. Normalized Bridge/simulator listing and canonical CCAPI info schemas remain separate. Generic camera-settings parsers are unchanged.
- Download continuation/worklist, stop-on-first-download-failure, delete behavior, JPEG-original admission and native RTP/LUT code are unchanged. This is not a persistent mutation queue and does not resume or replay operations automatically.
