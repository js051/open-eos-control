# Control Transports

Open EOS Control grows around a shared camera-control contract, not one protocol. UI code asks for camera actions; each backend decides how to perform them.

## Current Backend

### CCAPI network

- Status: implemented.
- Platforms: direct Android and iOS clients; PC uses the native CCAPI engine inside Desktop Bridge.
- Connection: Wi-Fi or wired network when the camera exposes CCAPI over HTTP/HTTPS.
- Current strengths: no driver, direct mobile/PC control, easy HTTP diagnostics, working JPEG Live View on R6 Mark III, strictly advertised writable settings and shutter/autofocus/focus-drive commands, complete lifecycle gating, paged media retrieval, Canon sample-backed bounded thumbnails and image/RAW display previews, and capability-gated deletion. Android and iOS implement Canon's advertised H.264 RTP path with persistent native decode surfaces; PC receives the same RFC 3550/RFC 6184 stream and decodes it through PyAV/FFmpeg for the Bridge JPEG contract.
- Auto Power Off uses only the exact same-version advertised `/functions/autopoweroff` GET/PUT contract. Documented timed values remain ordinary settings; `immediately` is excluded from that selector and enables a separate confirmed camera-sleep command only when the live ability contains it. Acceptance stops local Live View/event/media work and disconnects because Canon ends CCAPI while entering sleep.
- Sensor cleaning uses only an advertised `POST /functions/sensorcleaning`. Android, iOS and PC send the exact boolean `autopoweroff` body, require HTTP 200, pause event polling and Live View, and restore the active session unless clean-and-power-off was selected. The operation stays unavailable on libgphoto2 and Android USB until a reliable public command contract exists.
- Canon lens mount/name and temperature restrictions are status capabilities, not assumed camera defaults. They appear only after the exact advertised endpoints return documented payloads. Android, iOS and PC refresh temperature before restricted start commands and keep every corresponding stop/release path available; physical R6 Mark III endpoint and transition validation remains queued.
- Android routes camera HTTP and RTP UDP sockets only through the Wi-Fi network that reaches the camera, allowing cellular internet to remain available without process-wide network binding. Debug refresh takes a new Android network snapshot and reports whether the bound camera network is still present, validated cellular availability, current system-default transport and validation state; coexistence is true only for an available `WIFI_BOUND` camera network plus a validated cellular default network. A physical coexistence result is still required.
- Current tradeoffs: JPEG polling smoothness and latency depend on Wi-Fi, camera response time, and JPEG decode cost. RTP is exposed only when discovery advertises both required operations and the client has a routed camera-Wi-Fi IPv4 address. Every video and audio path still needs physical-camera validation. Android, iOS, and PC decode an advertised in-band AAC LATM/48 kHz stream; unsupported SDP/audio shapes stay unavailable.
- Device-validation queue: still capture, Bulb press/release, independent AF-ON, shutter half-press, movie recording, tap focus, Click White Balance, manual focus drive, media browser, media thumbnails, media download, and media deletion on EOS R6 Mark III.
- RTP status: Android, iOS, and PC H.264 video receive/decode is implemented and contract-tested. Android RFC 6416 `MP4A-LATM/48000` receive/reassembly, Media3 raw-AAC extraction, `MediaCodec` decode and `AudioTrack` output are covered by protocol, UDP-session, Compose and real Android codec tests. iOS performs independently bound UDP reception, bounded marker/timestamp reassembly, in-band AAC-LC LATM extraction, `AVAudioConverter` decode and `AVAudioEngine` playback, with a real AAC fixture decoded in the iOS test bundle. PC receive/decode-to-PCM and default-muted WebAudio playback are codec/browser tested. Every platform starts muted, stops playback in the background, bounds queued work and isolates audio failure from video. The last sanitized R6 Mark III report did not advertise RTP, so that camera correctly remains on JPEG polling until a new discovery report proves otherwise. Physical-camera RTP audio/video validation remains required.

## Wired Backends

### Android USB/PTP

- Status: standards-based backend and a focused Canon EOS vendor layer are implemented; EOS R6 Mark III device validation is required.
- Connection: Android USB host/OTG to camera USB.
- Current implementation: enumerate Android USB devices, request permission, claim a `06/01/01` Still Image interface, use buffered bulk transfers, open/close a PTP session, read DeviceInfo/storage/property descriptors and values, perform safe advertised standard property writes, list object metadata, stream object downloads to Android SAF destinations, and delete exact object handles only when `DeleteObject (0x100B)` is advertised.
- Standard still capture is enabled only when DeviceInfo advertises `InitiateCapture (0x100E)`. A successful response is reported as command acceptance; the physical result still needs an R6 Mark III validation record.
- Standard property controls are enabled only for writable camera-advertised descriptors with bounded options. Canon ISO/Tv/Av/WB controls separately require `0xC189/0xC18A` event state and use only camera-advertised choices with `SetDevicePropValueEx`; both paths still need an R6 Mark III validation record.
- Canon clock synchronization is exposed only after the camera emits `UTCTime (0xD17C)` or `CameraTime (0xD113)` and advertises the remote/event plus `SetDevicePropValueEx (0x9110)` path. The backend writes current Unix seconds as UINT32, prefers UTC time, and reports success only after a matching property event arrives within the bounded verification window.
- Canon still capture, half-press and Bulb require the full remote/event operation set. When host and card `CaptureDestination (0xD11C)` values plus the complete transfer/capacity path are advertised, Photo settings let the user choose Phone or Memory card and write the exact value. Phone capture uses `GetPartialObject` in 1 MiB chunks followed by Canon `TransferComplete`; completed files are atomically stored in app-private media and exposed through Media. RAW+JPEG transfer requests are all consumed. An explicitly selected Phone path that becomes unavailable aborts before shutter; unsafe inherited host state may fall back to an advertised card value. Capture is not reported as success until a card object event or completed host transfer arrives, and press/release commands are balanced on failure paths. In camera-advertised Bulb mode the app sends half/full press, holds it without active Live View polling, and releases full/half in reverse order; teardown also attempts release.
- Dual-card Canon bodies can expose `CurrentStorage (0xD11E)` in Photo settings. The selector exists only when its current value matches one of at least two writable IDs discovered from the connected camera; it re-reads those IDs before every exact UINT32 write and never hardcodes the R6 Mark III snapshot's CFe/SD IDs.
- Canon independent AF-ON prefers camera-advertised `DoAf (0x9154)` and `AfCancel (0x9160)`, holds focus for a bounded interval, and sends cancel in a non-cancellable cleanup path. The balanced remote-release half-press remains the fallback only when the dedicated pair is absent.
- Canon manual focus uses the advertised `DriveLens` operation with Near/Far steps 1-3. Canon JPEG Live View enables EVF mode/output, polls `GetViewFinderData`, and parses only validated JPEG block types. Conditional USB Touch AF additionally requires advertised `TouchAfPosition (0x915B)`, a complete balanced AF path, active Live View and bounded sensor geometry from viewfinder block `0x0E`; it sends `[3, x, y]` in sensor coordinates and reports success only after the position command and AF cycle succeed. Conditional USB Click White Balance requires advertised `ClickWB (0x9157)`, active Live View and the same bounded geometry; it sends exactly `[x, y]` without adding AF or guessing a white-balance mode.
- Camera and completed phone media expose display preview per item only for a positive-size JPEG/PNG object no larger than 32 MiB. Camera files use standard `GetObject`; host files use a bounded private-file read. Complete signatures are validated before display, while RAW/HEIF/video retain download without a preview action.
- Canon movie control writes `EVFRecordStatus (0xD1B8)` through `SetDevicePropValueEx`: Card (`4`) starts card recording and None (`0`) stops it. The capability is exposed only after camera events advertise both values; SDRAM (`3`) is treated as preview rather than recording.
- Canon shooting-mode control writes camera-advertised `AutoExposureMode (0xD105)` UINT16 values through `SetDevicePropValueEx`. The app's Photo/Video context synchronizes only when the writable `shootingmode` list proves a target value, and restores only a previously observed photo mode.
- The Canon mappings follow a pinned libgphoto2 revision and are test-covered. This includes capability-gated Auto Power Off (`0xD114`) with Canon-documented time values; the camera snapshot's unknown `0xFFFFFFFF` sentinel is diagnostic-only. They remain in device-validation status until exercised and recorded on the physical R6 Mark III.
- Next milestone: validate the standard and Canon paths, including movie start/stop, conditionally advertised Touch AF and conditionally advertised Click White Balance, on the camera, then map only measured property gaps. The pinned R6 Mark III snapshot exposes DoAf/AfCancel but neither `0x915B` nor `0x9157`, so both tap operations remain hidden unless the connected body itself advertises them.
- Research track: Canon vendor settings beyond the implemented shooting-mode, exposure, color, active-storage, aspect-ratio, power-zoom, Auto Power Off, image-quality, AF, drive, metering, movie, conditional Touch AF and conditional Click White Balance paths.
- Tradeoffs: best pure phone-to-camera wired path, but it requires a real PTP engine plus Canon vendor-extension testing.

### Desktop bridge and PC control

- Status: HTTP service, built-in PC control UI, directly executable Windows x64 bundle, libgphoto2 CLI engine, direct CCAPI engine, and Android/iOS clients are implemented and tested; EOS R6 Mark III device validation remains.
- Connection: the PC UI can control a USB camera through libgphoto2 or connect directly to the camera's wireless CCAPI origin. Its viewfinder can alternatively use a local browser `videoinput`, including the R6 Mark III's UVC mode or an HDMI capture card, while the original Bridge camera session continues to own camera commands. Android and iOS can use the same authenticated bridge for a computer-attached USB camera. The Windows standalone release requires no separate Python runtime for CCAPI or local video; USB still uses native gphoto2 when present or a capability-checked WSL 2 command prefix. WSL USB requires usbipd-win plus an explicitly attached camera.
- Engines: `libgphoto2` is the executable open-source USB path; `ccapi` is the executable HTTP(S) wireless path. The Canon EDSDK adapter remains optional research and no Canon binary is redistributed.
- Current implementation: both engines map into the same session/capability API. libgphoto2 provides camera discovery, dynamic settings, capture, independent AF-ON through a writable runtime `autofocusdrive`/`autofocuscancel` pair with balanced half-press fallback, explicit half-press, camera-advertised `Press Full`/`Release Full` Bulb control, movie target control, relative focus drive, persistent MJPEG preview with control-safe restart and bounded single-frame fallback, runtime-probed `--wait-event` body/media synchronization, media transfer, per-item JPEG/PNG display preview, and ability-gated deletion. Event waits are bounded and pause while persistent Live View or Bulb owns the USB camera. Camera clock synchronization requires a writable `syncdatetimeutc`/`syncdatetime` action paired with its DATE widget, prefers UTC, forces a fresh config readback, and records success only when the reported Unix time falls within ten seconds of the operation interval. Before still capture it forces a writable, camera-advertised `Memory card` target when available and refuses a known host-RAM target without one; host-RAM capture remains hidden. Its R6 Mark III setting map includes WB shifts, per-card image quality, aspect ratio, power-zoom speed, safe timed Auto Power Off choices and an active recording-card selector derived only from writable live `--storage-info` IDs plus the writable `storageid` widget. PC, Android Bridge and iOS Bridge share that Photo-only setting; every write strictly revalidates the cards and never uses snapshot constants. Each control still requires writable runtime choices, single-choice advanced controls are hidden, the undocumented `0xFFFFFFFF` sentinel is rejected by the API, and libgphoto2 does not advertise immediate camera sleep or sensor cleaning without a verified public CLI contract. CCAPI additionally provides capability-gated immediate sleep with confirmation and disconnect, confirmation-gated sensor cleaning with optional power-off, advertised-operation discovery, dynamic settings, capture/release, held Bulb press/release, AF-ON/half-press, recording, geometry-backed Tap AF/Click WB, focus drive, bounded JPEG polling, and advertised RTP H.264 through a routed UDP receiver plus PyAV decoder. RTP capability requires both Canon endpoints, a valid route and decoder; AUTO falls back to JPEG only after cleanup. The built-in responsive PC UI offers USB/CCAPI mode selection, Bulb elapsed time, Auto/RTP/JPEG selection when multiple sources exist, English/Traditional Chinese setting labels and key values, authenticated binary transfer, confirmed deletion and redacted diagnostics. Bridge Bearer tokens and camera passwords are memory-only; camera URL and username may be remembered. Loopback is the secure service default; LAN use requires a Bearer token.
- Local preview implementation: the browser requests video only, enumerates camera/capture-card inputs, switches sources without destroying the Bridge session, and stops every track on device/source/disconnect/page teardown. It records rolling frame rate and a small allowlist of non-identifying track settings; device IDs and labels remain in page memory and never enter diagnostics. The default loopback URL is a secure context for `getUserMedia`. Monitoring assists can analyze local frames, but Tap AF, Click White Balance, focus magnification and the current libgphoto2 focus-drive path remain disabled because local video provides neither Canon detail coordinates nor camera-side Live View state.
- Strengths: immediate access to mature libgphoto2 Canon mappings, including the checked-in upstream R6 Mark III capability snapshot.
- Tradeoffs: Android Bridge use requires a computer in the loop. Windows WSL USB additionally requires a WSL 2 distribution, gphoto2 inside it, usbipd-win, and explicit device attachment; while attached, the camera is not available to Windows applications. USB CLI preview keeps one `capture-movie` process for MJPEG and allows up to 30 FPS, but camera controls must briefly restart that process and physical R6 Mark III throughput remains unverified; fallback preview is capped at 5 FPS. A future native libgphoto2 adapter could avoid process restarts. Direct PC CCAPI defaults to 15 FPS and allows up to 30 FPS without claiming the camera will sustain it. RTP still decodes every H.264 access unit to preserve prediction state, while the requested FPS caps JPEG conversion/output. PC AAC LATM runs on a separate bounded socket/queue and authenticated PCM poll so a silent, malformed or unavailable audio stream cannot stop video.
- Local-preview tradeoffs: UVC/HDMI can provide a smoother monitor independently of the camera-control transport, but camera permission is browser-managed and the source's frame timing/format depends on the OS driver and capture hardware. Physical R6 Mark III UVC and HDMI capture-card behavior remains to be recorded.

### iOS CCAPI and Desktop Bridge

- Status: native Swift command/transport core and iOS 17 SwiftUI product UI are implemented and simulator-tested; physical iPhone and camera validation remain.
- Connection: iPhone/iPad can connect directly to camera CCAPI over Wi-Fi, or reach a PC over LAN and control its USB camera through Desktop Bridge.
- Current implementation: `ios/OpenEOSCore` provides direct CCAPI discovery plus a native authenticated Bridge client with service validation, USB discovery, camera selection and session cleanup. Both map capability-gated settings and commands, JPEG Live View, still capture, Bulb start/stop with elapsed time, independent AF-ON, half-press, recording, available focus operations, bounded media thumbnails, media download/deletion and redacted diagnostics into one app session. `ios/OpenEOSControl` adds mode-specific connection forms, Photo/Video control, manual focus drive when advertised, adjustable Live View, lazy thumbnail media rows, confirmation-gated media and Debug views, offline preview, English/Traditional Chinese selection, and safe portrait/landscape behavior. Direct CCAPI RTP additionally receives advertised in-band `MP4A-LATM/48000` on a separate Wi-Fi listener, extracts AAC-LC, and offers default-muted foreground playback with packet/decode/PCM diagnostics; audio bind, parse, or decoder failures never stop video.
- Automated evidence: macOS CI builds the final app bundle, verifies resources and network/orientation metadata, runs core/app unit tests, and completes English control/debug, media-deletion confirmation, Traditional Chinese connection, and offline Desktop Bridge form workflows on an iPhone Simulator.
- Next milestone: validate direct CCAPI and PC-attached USB Bridge paths on a physical iPhone and EOS R6 Mark III.
- USB/PTP stance: research track only until Apple platform constraints and public APIs are validated against Canon EOS bodies.

## Shared Backend Surface

Each backend should map into this surface:

- connect/disconnect
- camera identity and profile
- battery, camera status, and a shared storage summary containing availability, device count, total/free bytes, and remaining shots when the active transport reports them
- capability matrix and dynamic settings
- exposure, white balance, and generic setting writes
- camera clock synchronization where advertised, with each transport preserving its own verification limit
- timed Auto Power Off where advertised, plus immediate camera sleep only for a separately proven transport contract
- still capture, Bulb start/stop, half-press, recording, tap focus, Click White Balance, and focus drive where available
- media list/thumbnail/preview/download/delete where available, plus CCAPI protection/rating/display rotation only from an advertised and verified content-modification contract
- live view source, size, and FPS request

## Implementation Order

1. Keep CCAPI stable and improve diagnostics.
2. Validate the implemented Android USB/PTP session, DeviceInfo, storage, media, download, standard properties, and conditional standard capture paths on EOS R6 Mark III.
3. Validate the implemented Canon EOS remote release, native AF-ON/cancel, half-press, ISO/Tv/Av/WB, movie recording, manual focus drive, and JPEG Live View paths.
4. Record the remaining R6 Mark III vendor property/event gaps and add only mappings supported by reliable evidence.
5. Record whether R6 Mark III advertises `0x915B` and `0x9157`; when present, validate `0x0E` sensor geometry, Touch AF placement and balanced cleanup, plus Click White Balance sampling without an added AF command, before marking either device result passed.
6. Validate the implemented PC direct CCAPI and Android-to-desktop bridge paths with EOS R6 Mark III.
7. Measure persistent CLI MJPEG throughput, bounded event latency and control-restart latency on R6 Mark III, then consider a native libgphoto2 adapter only if it materially improves the recorded result or permits events during Live View.
8. Add an optional local EDSDK bridge adapter after SDK access, licensing, and supported host platforms are verified.
